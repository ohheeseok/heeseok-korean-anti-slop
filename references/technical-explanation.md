# 논문·기술 해설의 수사와 근거 구분

수식·수치·인용이 풍부한 문서에서도 제목과 결론에 캐릭터화, 반전형 구호, 포괄적 해결 선언이 겹칠 수 있습니다. 기술 내용의 존재나 검사기 후보 수만으로 문체의 적절성을 판단하지 않습니다. 먼저 전문 용어와 실제 동작을 보존하고, 장식적 표현과 주장에 필요한 근거를 구분합니다.

## L2-9. 기술 용어의 캐릭터화와 서사적 비유

| 검토 표현 | 문체를 다듬는 예시·방향 |
|---|---|
| 호라이즌 3형제 | 세 호라이즌의 정의와 역할. 원문의 기호와 세 항목 구분은 유지 |
| 다봉 액션 분포는 어떻게 살아남는가 | 디노이징 중 다봉 액션 분포의 변화. 기술적 성질을 미리 보장하는 결론으로 바꾸지 않음 |
| 정책 안에 예측 모델을 심는 행위 | 실제로 학습한다는 대상·적용 조건을 앞뒤 식에서 확인한 뒤 직접 설명. 별도 모듈을 삽입한다는 구현으로 해석하지 않음 |

친근한 설명이 모두 잘못된 것은 아닙니다. 작성자가 피하려는 캐릭터화·경구를 줄이는 것이 목적입니다. `에너지 지형`, `기울기장`, `액션 공간`, `호라이즌`, `노이즈 스케줄`, `정규화 상수`처럼 기술적 대상을 가리키는 말은 은유적 기원이 있다는 이유로 바꾸지 않습니다. 분야에서 쓰는 `정제`나 `디노이징`도 단어 자체만으로 판정하지 않습니다.

## L1-5 보완. 기술적 대조와 명령형 구호

`A하지 말고 B하십시오`가 서로 다른 처리 단계나 추상화 수준을 배타적인 선택으로 제시하는지 확인합니다. 예를 들어 본문에서 ‘노이즈 예측’과 ‘액션 시퀀스 예측’을 설명한 뒤 `액션을 예측하지 말고 정제하십시오`로 끝내면, 어떤 예측을 대체한다는 말인지 구분할 필요가 있습니다.

- 원문이 실제로 비교한 방법·출력·조건을 찾아 직접 설명합니다. 제목에 맞추려고 새로운 알고리즘 설명을 추가하지 않습니다.
- `관측은 조건으로 사용하고 출력에는 포함하지 않는다`처럼 실제 설계 차이를 설명하는 대조는 보존합니다.
- `원본을 수정하지 말고 복사본에서 작업하세요`처럼 행동 범위가 명확한 지시는 구호라는 이유로 바꾸지 않습니다.
- 요약이 본문과 긴장 관계에 있다고 해서 기술적으로 틀렸다고 확정하지 않습니다. 문서 내부의 어휘·범위 차이를 지적하고 필요한 근거를 따로 확인합니다.

## L1-12. 포괄적 해결·보장·대응 선언의 근거와 범위

`한 가지 변경으로 동시에 해결`, `정확히 일대일로 대응`, `구조적으로 보장`, `별도의 장치 없이 따라온다` 같은 표현은 주장을 읽기 좋게 닫아 주지만 조건을 생략할 수 있습니다. 자동으로 지우거나 완곡어로 바꾸지 말고 다음을 확인합니다.

1. **주장 종류:** 실험에서 관찰한 결과인지, 저자의 설명인지, 해설자의 해석인지, 조건 아래 증명한 명제인지 구분합니다. 원문에 없는 저자 귀속을 만들지 않습니다.
2. **조건과 범위:** 특정 태스크·설정·반복 구간의 결과를 모든 환경에 대한 보장으로 옮기지 않았는지 봅니다. 본문에 있는 추가 설계·아키텍처·조건을 요약이 생략했는지 대조합니다.
3. **대응 관계:** ‘세 난점’, ‘세 성질’, ‘일대일 대응’이라면 항목의 수뿐 아니라 의미와 대응 단위도 확인합니다. 뒤의 표에서 항목을 더했다면 추가 항목인지 다른 집계인지 확인하고 개수를 임의로 맞추지 않습니다.
4. **동치와 해석:** `X = Y`, `정확히 같은 구조`, `성질의 정체`가 수학적 동치인지 설명용 비교인지 확인합니다. 수식의 등호·근사 기호를 바꾸거나 해석을 정리로 격상하지 않습니다.

실험 관찰을 `논문이 보장한다`고 부르는 안내 문자열도 검토합니다. 본문뿐 아니라 버튼 뒤 안내·툴팁·차트 라벨·스크립트의 설명 문구까지 같은 기준을 적용합니다. 그리기 함수나 수식 계산 코드는 문체 교정 대상이 아닙니다.

### 문체 교정과 사실 검증의 경계

- 어순·중복·지칭 대상만 바꿔도 의미가 보존되면 그 범위에서 고칩니다.
- `보장한다 → 도움이 될 수 있다`, `해결한다 → 완화한다`처럼 근거 없이 주장의 강도를 낮추지 않습니다. 근거가 필요한 이유와 확인할 조건을 본문 밖에 적습니다.
- 실제 증명이나 정의가 있으면 `정확히`, `일대일`, `보장`을 유지할 수 있습니다. 강한 단어라는 이유로 부정확하다고 판정하지 않습니다.
- 원 논문을 읽지 않았다면 ‘논문도 이 주장을 한다’, ‘논문은 이렇게 말하지 않는다’고 쓰지 않습니다. HTML 내부의 대응·조건은 검토할 수 있지만 외부 출처의 기술적 참·거짓을 확인한 것으로 소개하지 않습니다.


## L1-12 보완. ‘X가 병목이다’로 끝내는 진단의 반복

‘병목’은 실제 성능 제한 요인을 가리키는 기술 용어일 수 있습니다. 그러나 문단마다 데이터·모델·조직·실행을 번갈아 병목으로 부르고 설명을 끝내면, 구체적인 제약을 생략한 진단형 상투어가 됩니다. 작성자가 피하려는 AI 말투로 검토합니다.

- **확인:** 무엇이 제한되는가(처리량·지연·성능 등), 어떤 요인이 그것을 제한하는가, 본문에 어떤 관찰·측정·논거가 있는가를 확인합니다. 모든 문장에 수치를 요구하지는 않습니다.
- **반복 판단:** 같은 진단 형식이 서로 다른 원인을 설명하는 자리를 대신하는지 봅니다. 도입의 논지를 결론에서 다시 언급하는 것만으로 남발이라고 단정하지 않습니다. 단순 횟수 기준을 만들지 않습니다.
- **표현 교정:** `정책 표현이 병목입니다`를 `정책 표현 방식이 성능을 제한합니다`처럼 실제로 제한되는 대상을 밝혀 바꿀 수 있습니다. 이는 문체 예시이며 해당 기술적 주장을 검증했다는 뜻은 아닙니다. 원문에 없는 수집 지연·메모리 부족·비용 증가 등의 원인을 추가하지 않습니다.
- **대상 불명:** 무엇을 제한한다는 뜻인지 원문에 없으면 본문 밖에 확인 사항을 적습니다. 병목을 ‘핵심’, ‘제약’, ‘장애물’ 같은 추상어로만 교체하고 설명이 좋아졌다고 보지 않습니다.
- **유지:** 프로파일링·대기열·대역폭 등에서 실제 제한 요인을 식별한 문장, 논문이 정의한 bottleneck, 반증·조건을 포함한 구체적 진단은 유지할 수 있습니다.
- **강도 보존:** `제한한다`는 주장을 근거 없이 `영향을 줄 수 있다`로 낮추지 않습니다. 문체 개선과 원인 규명의 사실 검증은 구분합니다.

## L3-2 보완. 전문적인 뜻과 어색한 결합 구분

- `한 모드에 커밋한다`: 해당 문맥에서 한 번의 rollout 동안 선택한 모드를 유지한다는 뜻인지 확인합니다. rollout 간의 다봉성과 rollout 내부의 일관성을 구분하며 ‘정책 전체가 한 모드만 낸다’로 바꾸지 않습니다. Git 커밋은 그대로 둡니다.
- `외부 교란에도 우아하게 반응했다`: 우아함이 실제로 어떤 관찰을 뜻하는지 확인합니다. 임의로 안정성·정밀도·성공률 수치를 보충하지 않습니다. 명시적인 성능 평가라면 그 정도도 보존합니다.
- `분포를 덮는다`, `엄밀한 이해를 끌어온다`: 기술적으로 대응하는 대상과 행위가 분명한지 봅니다. 비유를 지우다가 샘플링 공간·이론의 적용 범위를 지어내지 않습니다.

## 반드시 보존할 대조 사례

- 로봇이 `손잡이를 3회 이상 돌립니다`: 실제 물체·횟수·행동입니다. 손잡이라는 단어가 검사기에 표시돼도 유지합니다.
- `관측/예측/실행 호라이즌`, `기대 좌표`, `지도 학습`: 기술 용어입니다. `층`·`좌표`·`지도`의 비유 규칙을 일괄 적용하지 않습니다.
- `평가에서는 최대 4스텝 지연까지 성능을 유지했다`: 관찰의 범위를 보존하고 다른 지연·환경에 대한 보장으로 바꾸지 않습니다.
- 본문과 부록의 수치가 서로 다르다고 원문이 표시하면 두 값과 출처 구분을 유지합니다. 평균값으로 합치거나 임의로 하나를 정답으로 선택하지 않습니다.
- 출력 기호, 수식 번호, 부등식, 단위, 인용 번호를 보존합니다. 문체만 다듬을 때 새 수학적 유도나 제품·실험 설정을 추가하지 않습니다.
